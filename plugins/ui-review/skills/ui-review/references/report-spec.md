# Report specification

The report is one self-contained HTML page. `assets/report-template.html` implements everything below and renders it from one `<script type="application/json" id="audit">` block; you write only that JSON (`audit.schema.json`, examples in `assets/example-audit.json` (Ukrainian) and `assets/example-audit.en.json`). Rebuild from this spec only if the template cannot be used.

## Look

Annual-report style: white ground, black ink, one vermilion accent (#ff4a1c) only for the main problem, severity-4 marks and the top 3 fixes, amber for warnings; dark theme on #120d0b (the page follows `prefers-color-scheme` and a `data-theme` attribute on the root). Titles in Sofia Sans Condensed 800, text in Sofia Sans (both cover Latin and Cyrillic). Simple stroke SVG icons per lens, no emoji. It must work at 360px: tables become stacked cards, the screen route turns vertical, screenshots stack. Every derived number (ICE, UI health index, quick wins, confidence, pass rates, critical count) is computed by the template, never typed.

Headings state their point ("Half the phone buttons are too small to tap"), not a topic ("Touch targets"). If any data is sample or assumed, say so once in a small label at the top. Footer: generated by ui-review.

## Sections, in order

1. **Header** - headline = the main finding with its number; one-sentence lead; KPI row: UI health index (average of lens scores), the main failing check, one more key number, critical issues or quick wins. Then the **checks** block: horizontal bars of measured pass rate against a target (contrast, touch targets, labelled fields...), the worst one in vermilion; or a task-flow funnel when step numbers exist. Under it, the **UI maturity** strip (Broken, Usable, Consistent, Polished, Delightful; the current one filled) with one sentence on what blocks the next level.
2. **Lenses** - radar chart of all 12 lens scores (0-100, low = problems) beside a grouped list with meters (5 groups: look, use, reach, words, system).
3. **Annotated screens** - every screenshot with numbered boxes over the problem areas. The number is the opportunity id, so the reader can jump from a box to its plan entry; boxes of severity 4 and of the top 3 are vermilion, the rest ink. Caption: screen, viewport, URL. Without an image the frame is drawn hatched, with the marks, and says the screenshot is not attached.
4. **Screen route** - the main task as 4-8 screens: viewport or path, screen name, one-line pain, status ok / friction / blocking.
5. **Impact-effort matrix** - numbered dots per opportunity; filled = fix, outlined vermilion = rethink; quick-wins quadrant tinted; heading states how many quick wins.
6. **Issues table** - sorted by ICE, filter chips (all / fix / rethink / critical), columns: #, issue (with an observed/hypothesis badge), lens (icon + name), severity, type, I, C, E, ICE with bar; top 3 highlighted.
7. **Next 3 fixes** - cards with hypothesis ("If we X, then Y improves, because Z"), success metric, cheapest test.
8. **Full plan for every issue** - one collapsible row per issue, sorted by ICE, top 3 open, plus an "expand all" button. Summary: number, title, lens, severity, ICE, type, effort, badge. Body: **Why it is here** (the evidence: measured values, screenshot, owner's words), **Where** (page/URL, viewport, selector, a link to the mark on the screenshot), **Current → target** table (property, current, target, token; colour values get a swatch), **What to do** (concrete numbered steps), **Metric**, **Effort**, **Risk / guardrail**. Top 3 also show alternatives considered, experiment (risk type, success threshold), pre-mortem, and 2 copy variants when the change is about wording.
9. **Data and confidence** - the source list with statuses, a confidence meter (ok = 1, demo = 0.6, no = 0, averaged), the start questions with their answers, the design tokens found; a collapsible glossary of all terms; a collapsible "how this review was made".

## Data shapes and language

The full shape is in `audit.schema.json`; `scripts/validate_audit.py` checks it plus the skill's rules. The parts that are easy to get wrong:

- `lang` (`uk` or `en`) picks the interface labels from the template's `UI` dictionary. For another language, add an entry with the same keys.
- `text` holds the report's own words: `label`, `headline`, `lead`, `checksNote`, a heading `…H` and intro `…P` per section (`lenses`, `shots`, `screens`, `matrix`, `ops`, `next`, `plan`, `data`), `how`, `footer`. Tokens `{health}`, `{qw}` (quick wins), `{n}` (issues), `{conf}`, `{crit}` (severity-4 count) are filled in; `[[words]]` turns red. All text is escaped. A missing or empty key removes that element.
- `kpis`: up to 4 `{v, l, hot?, src?}`. A value with a literal number needs `src` = the name of an entry in `sources`.
- `checks`: `[{l, v, b, t, sub?, src?, hot?}]` - `v` of `b` pass, target `t` %. `v: null` shows "no data" with a hatched bar. Say in `checksNote` what was measured, on which screens and viewports.
- `maturity`: `{cur, note}`; `cur` 0 Broken … 4 Delightful.
- `shots`: `{id, src?, cap, url?, vp?, w, h, marks: [{n, x, y, w, h, note?}]}`; marks are in % of the image. `scripts/inspect_ui.py` prints these boxes for any selector. `build_report.py` turns a file path in `src` into a data URI (JPEG, ≤ 1280px wide keeps the page light).
- `ops`: `{t, l, ln, x: "opt"|"ex", ev: "obs"|"hyp", sev: 1-4, I, C, E}`; ids are 1-based positions. `detail` and `plans` are keyed by that id as a string.
- `detail[id].where`: `[{page?, url?, vp, sel?, shot?, mark?}]` - at least one entry, each with page or url, a viewport, and a selector or a shot id.
- `detail[id].change`: `[{prop, cur, tgt, token?, src?}]` - measured current value, target value, the token to use.
- `tokens`: `[{name, value, use?}]`.
- `answers`, `sources`, `glossary`: as in the schema.

## Tooltips for terms

Every abbreviation, metric and framework name in the report (WCAG, AA, ICE, CLS, CTA, Fitts's law, touch target, token, heuristic...) is a dotted-underlined button with a tooltip: the term, a 2-4 word gloss, and one or two plain sentences, ideally with this interface's own number ("#9AA0A6 on white = 2.6:1, needs 4.5:1").

- Desktop (a hover-capable fine pointer): opens on hover.
- Phones and tablets: opens on tap; a second tap or a tap elsewhere closes it.
- Keyboard focus opens it, Escape closes it; scrolling more than 40px closes it.
- Definitions live in one glossary object; the script wraps the first occurrence of each term per paragraph or cell.

## Mobile table cells

In the stacked (phone) table each cell is a flex row of label + value, so every cell's content is wrapped in one `<span class="cv">` - after terms are wrapped, and again after every filter re-render. On phones the I, C, E columns are hidden and shown inside the ICE cell ("576 = 8×8×9"). The current → target table in the plan stacks into label/value rows the same way.

## Robustness

- Charts are drawn at real pixel size with a ResizeObserver; bars and meters are HTML rows with a % width; marks are absolutely positioned boxes in % of the image, so they stay on target at any width.
- All script sits in one block at the end of `<body>`, wrapped in `{ }`; check it with `node --check` before delivery.
- `localStorage` is not needed; do not depend on it.
